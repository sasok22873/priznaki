# Настройка приглашений и подтверждения доступа

## Что делает эта версия

- Владелец приглашает человека по e-mail из вкладки **Команда → Доступы**.
- Edge Function проверяет JWT и роль владельца; ключ `service_role` не попадает в браузер.
- Приглашённый аккаунт создаётся со статусом `invited` и ролью `member` или `viewer`.
- До нажатия владельцем **Одобрить** пользователь не может открыть рабочие данные.
- Владелец может сменить роль или отозвать/вернуть доступ. Отзыв дополнительно ограничивается RLS в базе.

Роли: `owner` — полный доступ и управление людьми; `member` — просмотр общего пространства, создание задач и изменение только назначенных ему задач; `viewer` — только чтение.

## Установка

### 1. SQL в Supabase

В Supabase Dashboard → **SQL Editor** сначала запустите существующий базовый файл `team-access-migration.sql`, если он ещё не выполнялся. Затем запустите `supabase/migrations/20261108_team_approval.sql`.

Второй файл переводит новые профили в состояние ожидания, оставляет текущие профили активными и задаёт серверную проверку одобрения. Не запускайте его раньше базового SQL: он переиспользует RPC `update_own_profile` и `admin_update_profile` из базовой миграции.

Проверка после SQL:

```sql
select id, email, full_name, role, access_status
from public.profiles
order by created_at nulls last;
```

У текущего владельца должен быть `role = 'owner'` и `access_status = 'active'`.

### 2. Edge Function

Файл функции расположен по пути `supabase/functions/invite-member/index.ts`; настройка `supabase/config.toml` включает обязательную проверку JWT.

Из корня репозитория, где находится папка `supabase/`, выполните:

```bash
supabase login
supabase link --project-ref ВАШ_PROJECT_REF
supabase functions deploy invite-member
supabase secrets set APP_REDIRECT_URL="https://sasok22873.github.io/priznaki/"
```

Supabase обычно автоматически предоставляет Edge Functions `SUPABASE_URL`, `SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY`. Если в Logs функции написано, что секреты не заданы, настройте соответствующие секреты в настройках Supabase. **Никогда не помещайте `service_role` в `config.js`, `index.html` или браузерный код.**

### 3. Разрешить адрес возврата письма

В Supabase → **Authentication → URL Configuration** добавьте в Redirect URLs адрес сайта, например:

```text
https://sasok22873.github.io/priznaki/**
```

Убедитесь, что отправка e-mail приглашений настроена в Supabase Auth (SMTP / email provider). Ссылка приглашения приходит на адрес, указанный владельцем.

### 4. Файлы сайта

Замените в том же каталоге GitHub Pages оба файла:

- `index.html`
- `supabase-layer.js`

Остальные файлы из папки `supabase/` нужны в репозитории для деплоя Edge Function и миграций, но не должны загружаться как содержимое сайта. После commit дождитесь GitHub Pages и обновите страницу жёстко.

## Рабочий сценарий

1. Откройте **Команда → Доступы → Добавить участника**.
2. Укажите имя, e-mail и базовую роль. Отправьте приглашение.
3. Пользователь открывает письмо-приглашение, подтверждает e-mail и задаёт пароль на экране приложения. Пока статус **Ожидает одобрения**, рабочие данные ему недоступны.
4. Владелец проверяет запись и нажимает **Одобрить**. Статус станет активным; пользователю нужно войти заново с заданным паролем.
5. Изменить права можно в этой же вкладке. Отозванный пользователь теряет доступ к запросам Supabase сразу по RLS; для очистки уже открытого экрана ему следует выйти/обновить страницу.

## Что обязательно проверить после установки

- Приглашение отправляется, а запись появляется в `profiles` с `access_status = 'invited'`.
- До одобрения новый пользователь видит сообщение о неподтверждённом доступе.
- После одобрения у него появляется доступ согласно роли.
- `viewer` не может менять данные, `member` может создавать задачи и редактировать назначенные ему, `owner` управляет всем.

Эта версия использует приглашение владельца, а не открытую публичную регистрацию. Так новые аккаунты не могут самостоятельно получить доступ к проекту.
